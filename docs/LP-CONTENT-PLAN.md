## 1. ポジショニング

### 事実の再確認（現LPとのズレ）

現LPは2023年のメンヘラテクノロジー時代の案件しか載っておらず、**直近23ヶ月（正社員期）がまるごと欠落**している。
肩書も「フロントエンドエンジニア — React / Next.js / TypeScript」で止まっており実態と合わない。

実態:

- フロントエンドを軸に、**TypeScript の範囲でバックエンド（Hono / Drizzle / PostgreSQL）とインフラ（Google Cloud / Terraform / CI）まで縦断できる**
- Resme では一人でフロントからインフラまで通して機能を届ける体制を構築
- 生成AIを実装工程に組み込み、自分は要件整理・設計・レビューに集中する進め方を確立している

### 名乗り方

> フロントエンドを軸に、バックエンド・インフラまで並走できるエンジニア

- 「フルスタック」とは名乗らない（バックエンド言語が TypeScript に限られるため）
- 主戦場はフロントエンド、周辺は「並走できる」と書く

### 対応範囲の線引き（誠実に書く）

| できる | 書き方 |
|---|---|
| フロントエンド実装 | React / Next.js (App Router) / TypeScript。UI/UX の改善提案込み |
| バックエンド | **TypeScript のみ**（Hono / Drizzle / PostgreSQL / Supabase） |
| インフラ | Google Cloud / Terraform / CI・QA 整備 |
| 技術選定 | 構成の提案・判断ができる |
| 要件を詰める | **PM・シニアエンジニアと並走して**ヒアリングから詰めていける |

| 書かないこと | 理由 |
|---|---|
| 「要件定義を一人で担当」 | 抽象的な要件を単独で具体化するのは現状スキル外。盛らない |
| Ruby / Python / Go | 触ったことはあるが主戦力ではない |

## 3. 各セクションの中身

### ① Hero

**キャッチコピーは置かない。名前を大きく出すだけ**（本人決定）。

構成:

- ラベル: `PORTFOLIO — 2026`（mono）
- 名前: 「林田直樹」を display 級の明朝で最大まで大きく（`clamp(3.75rem, 15vw, 10rem)`）
- 英字名: `NAOKI HAYASHIDA`（mono）
- 立ち位置1行: 「フロントエンドを軸に、バックエンド・インフラまで並走するエンジニアです。」
- CTA: `お問い合わせ`（インク地に白抜きのピル）/ `経歴書を見る`（下線）
- 右下に技術スタックを mono で小さく

証拠数字は Hero には置かず、AI活用セクションと Works に分散する。

**この選択の帰結**: Hero が静かなぶん、「シンプルすぎる」の解消は
タイポの大きさ・紙の質感・入場モーション・下のセクションの中身が全部背負う。

### ② Now — いま作っているもの

**madoguchi**（2026年5月〜 / 個人開発 / [madoguchi.co](https://madoguchi.co/) 公開中）

- 住宅系事業者向けの「問い合わせ一次対応 + リード獲得」チャットボット
- 営業時間外に来た問い合わせを、翌営業日にすぐ追客できる情報に変えるのが狙い
- ナレッジに無いことは断定せず、金額や契約の話は有人へ渡す設計にしている
- スタック: Next.js 16 (App Router) / Hono / Vercel AI SDK v5 / Claude Haiku 4.5 / Drizzle ORM / PostgreSQL (Neon) / Cloudflare Workers / Resend / Playwright + Vitest

**このセクションの役割**: 「言われたものを作る人」ではなく「自分で課題を見つけて形にする人」の証明。

### ③ About — なぜフロントエンドなのか

一人称で語る。素材:

- HTML / CSS / JavaScript から入って、TypeScript → React → Next.js へ
- Rails も試したが、TypeScript が一番手に馴染んだ
- プロダクトがどうすれば伸びるか、ユーザー目線で UI を考えるのが好き
- 新しい技術のキャッチアップが好きで、動きが一番速いのがフロントエンドだった
- バックエンドもインフラも、必要になったから学んで触れるようになった

コーヒー要素はここに1行だけ差す（例: 週末はコーヒーを淹れている、レシピ管理アプリも作った）。
`coffeerepi` と Instagram への導線をここに置く。

### ④ How I work — 大事にしていること

本人の言葉に一番近い順:

1. **思ったことは、提案として出す**
   指示待ちにならない。UIで改善した方がいい所を見つけたら、自分から動かす。
   （会計事務所SaaS 13ヶ月：UI/UX の改善提案を起点にした開発でユーザーの入力負荷を下げた）

2. **ユーザーが自力で戻れる状態まで作る**
   （Resme：外部連携が切れた時に、検知して再連携へ導く動線を Web・Chrome拡張・通知メールに実装）

3. **規約をルール化して、品質のばらつきを潰す**
   TDD・型安全・技術スタックをルールファイル化して、実装時に必ず通るようにする。

### ⑤ AI-assisted development ★独立セクション

このLPの最大の差別化材料。ただし**「AIに書かせている」ではなく「品質を安定させる仕組みを作っている」**という書き方にする。

- Claude Code をメインに、実装は Codex CLI / Cursor CLI へ委譲
- 自作スキル **149本** / 専門エージェント **10種** / MCP連携（Notion・Slack・Figma・Playwright 等）
- 技術スタック・TDD・型安全といった規約をルールファイル化し、全セッションで強制
- 実装前に AsIs / ToBe / 制約 / テストケースを出させ、**承認してから着手する**フローを固定
- 設計判断とバグの原因を Markdown リポジトリに蓄積し、セッションを跨いで文脈を引き継ぐ

**効果**（そのまま書く）:
実装を委譲することで要件整理・設計・レビューに集中でき、構想を動く MVP まで持っていくサイクルが回るようになった。
ルール化により AI 生成コードでも品質のばらつきが減少した。

## 4. アートディレクション

### 方向

エディトリアル（読ませる版面）をベースに、**モーションと質感で密度を作る**。
罫線や番号で盛る方向には振らない（「一般的にUI/UXが良いと思われる」水準を優先）。

### 具体

| 要素 | 実装 |
|---|---|
| 見出し | Shippori Mincho B1（明朝） |
| 本文 | Zen Kaku Gothic New |
| ラベル・数値 | IBM Plex Mono |
| 配色 | **アクセントカラーなし（モノクロ）**。ただし純白・純黒は使わず、わずかに暖色に振ったオフホワイトとインクで質感を出す |
| CTA | 色ではなく**反転塗り**（インク地に白抜きのピル）で押し出す |
| レイアウト | 単一672pxをやめ、`9rem` のラベル列 + 本文列の2カラムグリッド。セクション番号とラベルを左レールに置く |
| 質感 | SVG feTurbulence の微細なグレイン + Hero に25%幅のヘアライングリッド |
| モーション | Hero の stagger 入場 / AI活用セクションの数値カウントアップ / madoguchi カードの hover 浮上 / セクション進入時の reveal。`prefers-reduced-motion` で全停止 |
| ダークモード | `next-themes` の手動トグルをヘッダーに追加 |

**Geist は使用をやめた**（そもそも変数定義だけで適用されておらず、実際は OS のシステムフォントで表示されていた）。
